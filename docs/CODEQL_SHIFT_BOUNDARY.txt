Dependency pin: db0ee5f431178f2153f9aa60581bd6ca59e89391, unchanged.
The iOS Kotlin path validates CubeState before invoking the C wrapper, and
returns immediately for a solved state. The C wrapper itself constructs a
std::string and calls the solver. Native Search::verify checks length=54,
maps stickers through centers, checks color counts, constructs cubies, then
calls CubieCube::check. These layers are not a general guarantee that direct
mutation of the public cubie arrays is supported.

Local reproduction compiled the pinned C++ sources using Apple Clang,
-std=c++14 -O1 -fsanitize=undefined -fno-sanitize-recover=undefined.
No pruning-table initialization or search was required:

1. Search s; s.verify("UUUUUUUUURRRRRRRRRFFFFFFFFFDDDDDDDDDLLLLLLLLLBBBBBBBBB");
   UBSan stops at CubieCube.cpp:280: signed left shift of
   1229782938247303440 by 4 cannot be represented in type long.
   This is an ordinary supported native-verifier input, not proof that the
   app's solved-state shortcut invokes the native verifier. The shift-base
   defect is distinct from the dismissed multiplication alert.

2. CubieCube c; c.edges[0] = -1; c.check();
   UBSan stops at CubieCube.cpp:97: shift exponent -1 is negative.
   This demonstrates unsafe direct array mutation, not app-input reachability.

3. A separate focused build used only
   -fsanitize=shift-exponent,signed-integer-overflow -fno-sanitize-recover=all.
   The native verifier accepted the solved string, rejected four malformed
   cases (53/55 characters, all-U, unknown sticker), and processed 1,000
   deterministic center-preserving balanced shuffles (mt19937 seed 19), all
   rejected, without diagnostics from these enabled checks. Shift-base
   checking was deliberately omitted in this focused build; this is NOT a
   full UBSan pass or exhaustive input-safety proof.

Harness and logs are retained locally in build/security-boundary-audit/.
